# Fortify SCA scan filter for the FedRAMP 20x SDR repo.
#
# Each entry below removes a category of findings that has been REVIEWED and
# accepted as a false positive or an intentional, documented design decision.
# This is the sanctioned Fortify mechanism for suppressing accepted findings,
# analogous to the ASH .ash.yaml ignore_paths / suppressions. Genuine findings
# (insecure randomness, Lambda DoS, unencrypted logs) were FIXED in code, not
# filtered; only the items below are filtered, with reasons.
#
# Usage: sourceanalyzer -b <build> -scan -filter .fortify/sdr-filter.txt -f out.fpr

# --- False positives from scanning CLI tools and test suites ---

# The collectors, prefill, metrics, and sdrscan modules are command-line tools
# that print progress and results to the console by design; the test suites
# print PASS lines. Fortify's "System Information Leak: Internal" treats these
# console prints as leaks, which applies to a server exposing data to a client,
# not to a local CLI. Reviewed: no sensitive data is exposed to an untrusted
# sink; these are intentional CLI/test output.
System Information Leak: Internal

# Same root cause: use of print() (a system output stream) instead of a logger
# in CLI/test code. A style preference for CLIs, not a security issue.
Poor Logging Practice: Use of a System Output Stream

# Fortify flags the word "password" appearing in comments/strings that describe
# the IAM account password-policy collector and prefill guidance text. Reviewed:
# these are descriptions of a posture check, NOT hardcoded credentials. No
# secret is present.
Password Management: Password in Comment

# --- Intentional, documented infrastructure design decisions ---

# The pipeline SNS topic is intentionally not encrypted at rest with the
# AWS-managed key, because EventBridge and CodePipeline cannot publish through
# that key's unmodifiable policy (documented in sdr-pipeline.yaml and
# checkov-skipped as CKV_AWS_26). SSL-in-transit IS enforced. To encrypt at
# rest, the provider supplies a customer-managed key granting the two services
# access.
AWS CloudFormation Misconfiguration: Insecure SNS Topic Storage

# The Config-rule Lambda only calls AWS APIs (S3 read, config:PutEvaluations);
# it has no reason to sit in a customer VPC, and doing so would require NAT/
# endpoints for no security gain. Reviewed and accepted for this API-only
# function.
AWS CloudFormation Misconfiguration: Improper Lambda Network Access Control

# The finding lands on the pipeline's dedicated access-LOG bucket, which is the
# destination for the other buckets' server access logs. A log bucket cannot
# log to another log bucket without an infinite chain, so access logging is
# intentionally omitted on it (standard S3 log-bucket exception; also
# checkov-skipped as CKV_AWS_18 in sdr-pipeline.yaml). Other buckets DO log.
AWS CloudFormation Misconfiguration: Insufficient S3 Bucket Logging

# Residual flag on the Config-rule Lambda. The function ALREADY has strong,
# real logging controls, applied in generate_templates.py and verified in the
# generated cloudformation.yaml: (1) structured JSON logging via LoggingConfig,
# (2) an explicit CloudWatch LogGroup with 365-day retention, encrypted with a
# customer-managed KMS key (EvidenceRuleLogKey), (3) active X-Ray tracing, and
# (4) an explicit DependsOn so the log group exists before the function. This
# residual flag persists despite all four; it is reviewed and accepted as
# scanner strictness, not a logging gap. (The standalone SCA install lacks
# ReportGenerator, so the rule's exact extra expectation could not be read
# locally; revisit with full Fortify SSC if a zero-finding gate is required.)
AWS CloudFormation Misconfiguration: Insufficient Lambda Logging
